## 1. Принципы и топология

1. **0 ₽ на инфраструктуру.** Все компоненты — free-тарифы: Render (web), Neon (PostgreSQL), cron-job.org / UptimeRobot (пингер), Cloudflare Tunnel (резерв плана C).
2. **Скелет деплоя — утром первого дня** (T-2, 10:00–11:00). Ранний деплой пустого проекта нужен не для кода, а для проверки главного инфраструктурного риска R4: *доступен ли домен `*.onrender.com` из сети площадки и у мобильных операторов гостей*. Если нет — план B включается сразу, а не за час до вечеринки.
3. **Всё воспроизводится из репозитория:** `render.yaml`, `requirements.txt`, `.env.example`, фикстуры каталога. Развёртывание с нуля — ≤30 минут по этому документу.
4. **Три уровня готовности, решение о переключении принимает админ:**

```
План A (основной)          План B (запасной)            План C (аварийный)
Render free + Neon    →    PythonAnywhere + SQLite  →   Ноутбук + cloudflared
холодный старт ~1 мин      always-on, без сна           запуск ~10 мин,
750 ч/мес на workspace     1 web app, диск постоянный   URL меняется при каждом
HTTPS из коробки           HTTPS из коробки             запуске (QR перепечатать)
время переключения: —      ≤30 мин (заготовка на T-2)   ≤10 мин (заготовка на T-2)
```

**Точка решения по плану B:** T-1, 15:00 — если смоук-тест с сети площадки / мобильных операторов не прошёл (страница не открывается, бесконечная загрузка, TLS-ошибки).
**Точка решения по плану C:** день T, если за 1 час до старта основной URL недоступен >5 минут и план B тоже не отвечает.

**Правила обращения с секретами:**
- `.env` — в `.gitignore` с первого коммита (до того, как в него что-то записали).
- На Render секреты вводятся в envVars вручную (`sync: false` в Blueprint) — в репозитории их нет.
- `ADMIN_PASSWORD` генерируется один раз на T-2, организатор получает его лично; в шпаргалке (§05) и на печати пароль НЕ указывается.
- Проверка перед релизом: `git log -p | grep -i password` пуст; в репо нет `.env`, `*.dump`.

## 5. База данных Neon

Пошагово (15 минут, входит в слот T-2 10:00–11:00):

1. neon.tech → Sign in через GitHub → **Create project** `tykvogolos`, регион **Frankfurt (eu-central-1)** — ближайший к площадке и, главное, *в том же регионе, что и выбранный для Render* (межсервисная задержка важнее задержки до гостей).
2. Plan — Free. Compute: 0.5 CU, autosuspend — оставить **300 s (5 мин)** по умолчанию.
3. Скопировать **Pooled connection string** (хост содержит `-pooler`) → `DATABASE_URL` (Render и локальный `.env`).
4. Для `pg_dump` с ноутбука (§13) использовать **Direct connection string** (без `-pooler`).
5. Миграции накатываются автоматически в Build Command — руками в БД не ходим.

**Лимиты и наши объёмы:**

| Параметр | Лимит free | Наш прогноз | Запас |
|---|---|---|---|
| Хранилище | 0.5 ГБ | ~38 субъектов × ~100 КБ фото + <2000 голосов ≈ **6–8 МБ** | ×60 |
| Compute-часы | 100 CU-ч/мес | событие ~6 ч + деплои/тесты ~10 ч + прогрев по расписанию ~15 ч ≈ **30–35 ч** | ×3 — **но только при дисциплине пингера (§7.3)** |
| Соединения | pooled через pgbouncer | Gunicorn 2×4 = ≤8 + pg_dump редко | ок |

**PITR:** на free-плане окно восстановления из истории ограничено (часы; точное значение — в консоли, раздел Restore). Считать PITR *приятным бонусом*, а не основным бэкапом. Основные средства восстановления — CSV-контрольные точки и `pg_dump` (§13).

### 6.2 Повседневные деплои

- Auto-deploy из `main` включён **только до T-1 17:00**. После финального деплоя auto-deploy выключить (Settings → Auto-Deploy → No) — случайный пуш в разгар вечеринки недопустим. Все изменения вечером T-1 — только через **Manual Deploy → Clear build cache & deploy** с телефона/ноутбука админа.

## 7. Прогрев: `/healthz` и пингеры

### 7.1 Эндпоинт `/healthz`

Греет и Render (HTTP-запрос), и Neon (`SELECT 1` не даёт compute уснуть):

```python
from django.db import connection
from django.http import HttpResponse

def healthz(request):
    try:
        with connection.cursor() as cursor:
            cursor.execute("SELECT 1")
        return HttpResponse("ok", content_type="text/plain")
    except Exception:
        return HttpResponse("db unavailable", status=503, content_type="text/plain")
```

Никакой авторизации, никакого кэша (`Cache-Control: no-store`), вес ответа — байты.

### 7.2 Настройка пингеров (два независимых, оба free)

**cron-job.org (основной):**
1. Регистрация → **Create cronjob**.
2. URL: `https://tykvogolos.onrender.com/healthz`, метод GET.
3. Schedule: **Execution every 5 minutes**.
4. Уведомления: on failure + on recovery, e-mail (при желании — webhook в Telegram-бота).

**UptimeRobot (контрольный):** New monitor → HTTP(s) → тот же URL → interval 5 min. Бонус: публичная status-страница — можно открыть на втором экране и видеть зелёные квадратики.

### 7.3 Расписание пингера — ОБЯЗАТЕЛЬНО (экономим 100 CU-ч Neon)

Круглосуточный пингер = ~730 compute-часов в месяц = **банкротство лимита Neon free за 4 дня**. Работаем по расписанию:

| Момент | Действие |
|---|---|
| T-2, после скелетного деплоя | Пингеры созданы, но **на паузе**. Прогрев — только ручными заходами при разработке |
| T-1, 17:00 (финальный деплой) | **Включить оба пингера.** С этого момента сервис и БД постоянно тёплые |
| T, событие + 2 часа | **Выключить оба пингера** (в чек-листе §12 — отдельный пункт) |

Итого прогрев ~30–35 ч — в пределах лимита с запасом. Если пингер забыли выключить — Neon приостановит compute при исчерпании CU-часов (данные не теряются, сервис начнёт отвечать 503 на `/healthz`) — заметим по уведомлению.

### 7.4 Ручной прогрев перед стартом (двойная страховка)

За 60 минут до открытия голосования — `scripts/warmup.sh` с ноутбука админа (или просто открывать `/` раз в 2–3 минуты):

```bash
#!/usr/bin/env bash
URL="${1:-https://tykvogolos.onrender.com}"
for i in $(seq 1 20); do
  code=$(curl -s -o /dev/null -w "%{http_code} %{time_total}s" "$URL/healthz")
  echo "$(date +%H:%M:%S) healthz: $code"
  sleep 150
done
```

Холодный старт, если случился: первый запрос висит ~30–60 с — это НЕ падение, гостям в этот момент показывается экран загрузки; повторный запрос уже быстрый.

## 8. План B — PythonAnywhere + SQLite

**Когда:** `*.onrender.com` недоступен из сети площадки/у операторов (R4), или Render нестабилен в окне события (R7). **Заготовка делается на T-2 вечером (20–30 мин), переключение в день T — ≤30 мин.**

**Почему SQLite:** на free-тарифе PythonAnywhere нет PostgreSQL (только MySQL и файлы). Для ~100 гостей и <2000 строк голосов SQLite на постоянном диске PA — надёжное и даже более быстрое решение (нет сети до БД, нет холодных стартов вообще — PA-приложения always-on).

### 8.1 Настройка (один раз, на T-2)

1. Зарегистрировать аккаунт `<user>` на pythonanywhere.com.
2. **Web → Add a new web app → Manual configuration → Python 3.12.**
3. Bash-консоль:
   ```bash
   git clone https://github.com/<org>/tykvogolos.git && cd tykvogolos
   python3.12 -m venv ~/.venvs/tykvogolos
   ~/.venvs/tykvogolos/bin/pip install -r requirements.txt
   cp .env.example .env   # DATABASE_URL=sqlite:///data/db.sqlite3, ALLOWED_HOSTS=<user>.pythonanywhere.com
   ~/.venvs/tykvogolos/bin/python manage.py migrate
   ~/.venvs/tykvogolos/bin/python manage.py collectstatic --noinput
   ```
4. **Web-вкладка:** в WSGI-файл — до импорта приложения:
   ```python
   import os, sys
   sys.path.append("/home/<user>/tykvogolos")
   os.environ.setdefault("DJANGO_SETTINGS_MODULE", "tykvogolos.settings.prod")
   # env-переменные: загрузить из /home/<user>/tykvogolos/.env (python-dotenv или вручную os.environ)
   ```
   Static files mapping: URL `/static/` → directory `/home/<user>/tykvogolos/staticfiles/`.
5. Web-вкладка → **Reload**. Проверить `https://<user>.pythonanywhere.com/healthz`.

### 8.2 Ограничения PA free (знать заранее)

- Одно web-приложение; раз в 3 месяца нажимать «Run until …» (поставить напоминание — для нашего окна неактуально, но пусть будет).
- Исходящий трафик — по whitelist (нам наружу не нужно — неактуально).
- `ADMIN_PASSWORD` и секреты — в своём `.env` на PA (отдельные от Render, не переиспользовать).

### 8.3 Переключение в день T (≤30 мин)

1. Решить: план B (фиксация в журнале, сообщение помощнику).
2. Если в Render-БД уже есть боевые справочники → перенос через фикстуру (§8.4). Если голосов ещё нет — просто проверить каталог глазами.
3. `/admin/qr` на PA сгенерирует QR **уже для PA-URL** (страница QR строит ссылку от текущего Host — заложить это в реализацию на T-1!) → перепечатать постеры или разослать новую ссылку в чат вечеринки.
4. Смоук: полный проход голосования с 2 телефонов через сеть площадки.

### 8.4 Перенос справочников между планами

Каталог (участники + группы, фото включены) всегда выгружается в фикстуру — это же «золотая копия» на случай полного пересоздания:

```bash
python manage.py dumpdata core.participant core.group --indent 2 -o fixtures/catalog.json   # на источнике
python manage.py loaddata fixtures/catalog.json                                            # на приёмнике
```

Обновлять `catalog.json` после каждого изменения справочников на T-1 (входит в чек-лист §12 утра).

## 9. План C — ноутбук + Cloudflare Tunnel

**Когда:** и A, и B недоступны (например, площадка легла вместе с внешним интернетом у провайдера, но есть мобильный хотспот). **Заготовка на T-2:** на ноутбук админа установлены Python 3.12, зависимости, бинарь `cloudflared`, скачана свежая `fixtures/catalog.json`. Время развёртывания — ~10 минут.

```bash
# 1. Локальный запуск (SQLite, настройки prod, DEBUG=0)
cd tykvogolos
python manage.py migrate && python manage.py loaddata fixtures/catalog.json
gunicorn tykvogolos.wsgi:application --bind 127.0.0.1:8000 --workers 1 --threads 8 &

# 2. Туннель наружу (без аккаунта Cloudflare)
cloudflared tunnel --url http://localhost:8000
# → в логе: https://<случайное-имя>.trycloudflare.com
```

**Особенности и риски (принять осознанно):**
- URL случайный и меняется при каждом запуске → старые QR мертвы. Способ доставки ссылки гостям: большой QR на проекторе (страница `/admin/qr`) + ссылка в чат вечеринки + озвучить со сцены.
- Ноутбук: заряд ≥80 %, питание рядом, сон отключён, обновления ОС приостановлены.
- Интернет: мобильный хотспот помощника (лимит трафика не критичен — страницы <300 КБ).
- Голоса хранятся в SQLite на ноутбуке → экспорт CSV после завершения + копия файла БД на телефон/флешку.
- Это **последний рубеж**: сценарий «всё сгорело». Именно поэтому он обязан быть отрепетирован 10 минут на T-2.

## 13. Бэкапы и восстановление

### 13.1 Контрольные точки CSV (основное средство, RPO ≤5 мин)

Экспорт из `/admin/export/` в фиксированные моменты: **(1)** T-1 после заполнения справочников, **(2)** T перед открытием, **(3)** T сразу после завершения, **(4)** опционально — в середине голосования. Файлы копировать с ноутбука на телефон/облако (правило 2 копий).

### 13.2 pg_dump (план A)

```bash
# с ноутбука, direct-строка Neon (без -pooler)
pg_dump "postgresql://user:pass@ep-xxx.eu-central-1.aws.neon.tech/neondb?sslmode=require" \
  -Fc -f backups/tykvogolos_$(date +%F_%H%M).dump

# восстановление (в свежую БД или поверх — осторожно, --clean)
pg_restore --no-owner --clean --if-exists \
  -d "postgresql://user:pass@ep-xxx.eu-central-1.aws.neon.tech/neondb?sslmode=require" \
  backups/tykvogolos_YYYY-MM-DD_HHMM.dump
```

### 13.3 Neon PITR (бонус, не основа)

Консоль Neon → проект → **Restore / Create branch from point in time** → выбрать момент → получить новую ветку-БД → подменить `DATABASE_URL` на Render → Manual deploy. Окно истории на free ограничено — проверять фактическое значение заранее; для окна «вечеринка» (3–4 ч) обычно достаточно.

### 13.4 SQLite (планы B/C)

```bash
sqlite3 data/db.sqlite3 ".backup 'backups/db_$(date +%F_%H%M).sqlite3'"   # горячая копия, безопаснее cp
```

### 13.5 Сценарии восстановления

| Что потеряно | Чем восстанавливаем | RTO |
|---|---|---|
| Голоса за последний час (сбой при записи маловероятен — транзакции) | PITR-ветка на момент час назад + ручной дозабор невозможен → переобъявление | ≤15 мин |
| Вся БД Render (удаление/коррапция) | `pg_restore` из последнего `.dump` в новый Neon-проект → смена `DATABASE_URL` | ≤15 мин |
| Справочники (случайный полный сброс) | `loaddata fixtures/catalog.json` (голоса при этом уже потеряны — поэтому сбросы только после экспорта!) | 5 мин |
| Платформа целиком (Render+Neon down) | План B/C + `catalog.json` + последний CSV голосов | ≤30 мин |

## 14. Мини-runbook инцидентов

Диагностика всегда начинается с двух вкладок: **Render → Logs** и **UptimeRobot**. Дальше по таблице:

| Симптом | Вероятная причина | Действия (по порядку, ≤5 мин) |
|---|---|---|
| `/` крутит загрузку 30–60 с, потом открывается | Холодный старт Render free | Норма после простоя. Повторный запрос быстрый. Включить/проверить пингер |
| 502 Bad Gateway | Gunicorn упал/перезапустился | Render → Logs: трейсбек? Сервис поднимется сам; если цикл — Rollback на предыдущий деплой |
| `/healthz` = 503 `db unavailable` | Neon уснул или недоступен | 2–3 повторных запроса (разбудят); Neon console → проект активен? CU-часы не исчерпаны? |
| Отправка голоса → 409 `not_active` | Состояние не ACTIVE | Дашборд → бейдж состояния; пауза? → `ПРОДОЛЖИТЬ` |
| Отправка → 409 `already_voted`, гость клянётся, что не голосовал | Общий телефон/чистка cookie (T1) | Норма принятого риска. Вежливо объяснить; при массовости — смотреть аномалии по IP-хэшам |
| Отправка → 422 `conflict` | Гость обошёл UI и выбрал кандидата дважды | Сервер отработал корректно; гостю — обновить страницу (черновик восстановится) |
| Логин админа не пускает | Лок после 5 попыток | Ждать 10 мин или перезапустить сервис (кэш в памяти воркеров сбросится) |
| Забыт `ADMIN_PASSWORD` | — | Render → envVars → новое значение → Manual deploy (перезапуск перечитает env) |
| Фото участника не грузится в карточке | Большой оригинал/битый файл | Перезалить фото в `/admin/participants/` (ресайз на сервере); кэш браузера — ETag обновит |
| Всё мертво и событие идёт | Платформенный сбой (R7) | План C: ноутбук + cloudflared, 10 мин; помощник объявляет гостям новую ссылку/QR с проектора |
