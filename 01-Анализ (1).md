# 01. Детальный анализ проекта

Сервис голосования для конкурса хеллоуинских костюмов · версия 1.0 · 2026-11-04

---

## 1. Контекст и бизнес-предпосылки

На хеллоуинской вечеринке проводится конкурс костюмов в 4 номинациях + гран-при.
Организатору нужен способ быстро собрать голоса гостей и посчитать результаты, а гостям — проголосовать «здесь и сейчас», не отрываясь от веселья.

**Жёсткие ограничения проекта:**

| Ограничение | Значение | Следствие |
|---|---|---|
| Срок | мероприятие через 3 дня, запуск за 1 день | только MVP, никаких экспериментов, деплой-скелет в первый же день |
| Бюджет | 0 ₽ | только free-тарифы (Render + Neon / PythonAnywhere) |
| Стек | Python | Django как самый быстрый путь «из коробки» |
| Масштаб | ~100 голосующих за вечер | нагрузка ничтожна; запас закладываем ×5 |
| Регистрация | запрещена требованием | идентификация — анонимный токен, защита от накрутки «мягкая» |
| Сеть на площадке | неизвестна (возможно перегруженный Wi-Fi) | страницы лёгкие (<300 КБ), статика без внешних CDN |

## 2. Цели и критерии успеха

**Цель сервиса:** собрать честные голоса гостей за 2–3 часа мероприятия и выдать результаты на экран со сцены за ≤5 минут после закрытия голосования.

Измеримые критерии успеха:

1. **Охват:** проголосовало ≥70 % гостей мероприятия.
2. **Скорость:** медианное время одного голосования ≤2 минут (от скана QR до экрана «спасибо»).
3. **Отказоустойчивость:** 0 инцидентов потери данных; доступность в окно мероприятия ≥99,5 %.
4. **Результаты:** подсчёт и вывод на проектор (полноэкранная диаграмма) ≤5 минут после закрытия.
5. **UX:** ни один гость не спросил «а где регистрироваться?» — её просто нет.

## 3. Целевая аудитория и роли

### Персона 1 — Гость «Гена» (голосующий)
- 20–45 лет, смартфон в одной руке, бокал/еда в другой, вокруг шумно и темно.
- Мотивация: поддержать друзей, поучаствовать в конкурсе, получить удовольствие.
- **Ожидание:** «тык-тык-тык — готово». Любая регистрация/SMS/почта = закрыл вкладку навсегда.
- Боли: длинные формы, мелкий текст, тусклые экраны в тёмном зале (тёмная тема здесь кстати), «а мой голос засчитался?».

### Персона 2 — Участница «Оля» (владелец костюма)
- Хочет победить; следит, чтобы её карточка (имя, номер, фото) была корректной.
- Может прислать друзьям ссылку «голосуйте за меня» → источник риска внешней накрутки (см. §7).

### Персона 3 — Организатор «Макс» (админ)
- Один человек с ноутбуком, часто параллельно ведёт мероприятие.
- Утром в день ивента добавляет/правит участников, вечером — стартует голосование, следит, закрывает, выводит результаты на проектор.
- Боли: сложный интерфейс, страх «нажать не туда и всё сломать».
- **Ожидание:** одна панель, крупные понятные действия, защита от случайных кликов (двойные подтверждения), экспорт результатов, возможность всё сбросить при аварии.

## 4. Ключевые сценарии использования

### 4.1 Гость: голосование (основной поток)
```
QR-код на столе/постере → главная = экран голосования (сразу!)
→ Номинация 1 «Самый страшный»: сетка карточек → тап по карточке → «Далее»
→ Номинация 2 «Самый смешной» → … → Номинация 4 «Лучший групповой»
→ Гран-при «Лучший костюм вечера» (участники + группы)
→ Экран подтверждения: сводка выборов → «Подтвердить голос»
→ Экран успеха: «Голос улетел в котёл!» + гарантия, что голоса учтены
→ Повторный заход с этого устройства: «Вы уже проголосовали» + благодарность
```
Любую номинацию можно **пропустить** («Не определился»). До финального подтверждения можно **вернуться назад** и поменять выбор.

### 4.2 Гость: заход вне окна голосования
- `НЕ НАЧАТО`: «Двери склепа ещё закрыты. Голосование откроется на мероприятии» (без обратного отсчёта к точному времени — время старта решает админ).
- `ПАУЗА`: «Голосование на паузе — ведьмы вышли на кофе ☕». Черновик (если был) сохраняется.
- `ЗАВЕРШЕНО`: «Котёл запечатан 🔮» + (опционально) ссылка на опубликованные результаты.

### 4.3 Организатор: подготовка (день до / утро дня ивента)
```
/admin → логин/пароль → дашборд
→ Участники: добавить (имя, номер, описание, фото) ×N
→ Группы: добавить (название, состав из участников, фото) ×M
→ Проверить карточки глазами гостя (предпросмотр)
→ Напечатать QR-коды (страница /admin/qr)
→ Голосование остаётся в статусе «НЕ НАЧАТО» (по умолчанию)
```

### 4.4 Организатор: мероприятие
```
Старт (двойное подтверждение) → дашборд: счётчики проголосовавших по минутам
→ [опц.] Пауза на время шоу → Продолжить
→ Завершить (двойное подтверждение) → Результаты: таблицы + диаграммы
→ Полноэкранная диаграмма на проектор (отдельная страница каждой номинации)
→ Экспорт CSV/JSON себе на ноутбук → [опц.] Опубликовать результаты гостям
```

### 4.5 Аварийные потоки
- Случайная накрутка/сбой → Опасная зона: «Сброс голосов» (участники остаются) или «Полный сброс» — оба с двойным подтверждением и настоятельной рекомендацией сначала сделать экспорт.
- Гость очистил cookie / зашёл с другого телефона → технически сможет проголосовать снова. Система это не блокирует жёстко (см. §7), но админ видит аномалии (голосов больше, чем гостей).

## 5. Функциональная декомпозиция

| Модуль | Состав |
|---|---|
| **М1. Голосование** | Экраны состояний; 4 номинации + гран-при; выбор одного кандидата; уникальность кандидата между номинациями; пропуск; черновик; атомарная отправка; экраны «проголосовал»/«уже голосовал» |
| **М2. Идентификация** | Анонимный voter-токен (cookie + localStorage), отметка «проголосовал» на сервере, логирование IP-хэша для детекции аномалий |
| **М3. Управление состоянием** | Статус-машина: НЕ НАЧАТО → АКТИВНО ⇄ ПАУЗА → ЗАВЕРШЕНО; переходы только из админки, с двойным подтверждением |
| **М4. Админка: справочники** | Auth (логин/пароль из env, троттлинг); CRUD участников; CRUD групп (состав); фото с ресайзом и хранением в БД; мягкое удаление |
| **М5. Админка: результаты** | Сводные таблицы; столбчатые диаграммы по каждой номинации и гран-при; полноэкранная страница каждой диаграммы; публикация результатов (опц.) |
| **М6. Экспорт** | CSV (голоса, участники, группы, свод результатов), JSON; UTF-8 BOM для Excel |
| **М7. Опасная зона** | Сброс голосов; полный сброс; журнал действий админа |
| **М8. Инфраструктура** | /healthz (пингер), rate-limit, WhiteNoise-статика, миграции при старте, логирование |

## 6. Правила голосования (формально)

1. Номинации: `SCARY` (Самый страшный), `FUNNY` (Самый смешной), `ORIGINAL` (Самый оригинальный), `GROUP` (Лучший групповой костюм). Кандидаты: первые три — участники, `GROUP` — группы.
2. Гран-при `GRANDPRIX` (Лучший костюм вечера): кандидаты — участники **и** группы (решение D-4).
3. В каждой номинации один голосующий выбирает **не более одного** кандидата (0 — если пропустил).
4. **Один и тот же кандидат не может быть выбран одним голосующим более чем в одной из 4 номинаций.** Кандидат, выбранный в номинации, блокируется в остальных (визуально + серверная валидация).
5. Гран-при **не конфликтует** с номинациями: кандидат, выбранный в номинации, может быть выбран и в гран-при (прямое требование заказчика).
6. Участник может одновременно выступать соло и входить в группу — это разные сущности, правило 4 их не связывает.
7. Голосование валидно только в состоянии `ACTIVE`. Отправка — один атомарный запрос со всеми выборами.
8. После успешной отправки голосующий не может изменить голос (только сброс админом).

## 7. Честность голосования: модель угроз

Регистрации нет → абсолютная уникальность невозможна. Осознанно выбираем **скорость вместо жёсткой защиты**: конкурс дружеский, главный «арбитр» — организатор с инструментами сброса и аналитикой аномалий.

| # | Угроза | Вероятность | Ущерб | Меры | Остаточный риск |
|---|---|---|---|---|---|
| T1 | Повторный голос того же гостя (инкогнито, чистка cookie, второй телефон) | Средняя | Средний | Токен в httpOnly-cookie (30 дней) + дубль в localStorage + отметка на сервере; IP-хэш пишется в лог для разбора аномалий | Принят. Админ видит `голосов > гостей` и может сбросить |
| T2 | Внешняя накрутка (участник расшарил ссылку в соцсети) | Средняя | Высокий | Голосование открывается только на мероприятии и закрывается в тот же вечер; окно голосования короткое; лимит голосов с одного IP-хэша (мягкий, по умолчанию выключен — на площадке общий NAT); лог аномалий | Средний→низкий |
| T3 | Скриптовая накрутка (бот) | Низкая | Высокий | Обязательный серверный токен, rate-limit (IP+токен), CSRF-защита, honeypot-поле в форме, валидация всех правил на сервере | Низкий |
| T4 | Голосование «за друга» с его телефона на площадке | Высокая | Низкий | Технически неустранимо; регулируется правилами конкурса организатором | Принят |
| T5 | Компрометация админки | Низкая | Критический | Логин/пароль из env (не в коде), HTTPS, троттлинг (5 неудач → лок 10 мин), отдельная неочевидная секция URL, сессии httpOnly/Secure | Низкий |
| T6 | Потеря данных (сбой платформы) | Низкая | Критический | Neon PITR + контрольные точки CSV-экспорта админом + `pg_dump` на ноутбук перед закрытием | Очень низкий |

## 8. Edge cases и каталог спорных решений

| # | Ситуация | Решение |
|---|---|---|
| E1 | В номинации `GROUP` нет ни одной группы | Экран номинации: «Кандидатов пока нет 🕸️», автопереход далее; не блокирует отправку |
| E2 | Участник удалён после получения голосов | Только мягкое удаление (`is_active=false`): голоса и итоги сохраняются, в результатах помечается «(снято)» |
| E3 | Гость начал голосовать, админ поставил ПАУЗУ | Черновик в localStorage жив; отправка отклоняется с понятным сообщением; после возобновления гость продолжает с того же места |
| E4 | Две вкладки, двойная отправка | Сервер: `UNIQUE(voter, category)` + транзакция; второй POST → экран «Вы уже проголосовали» |
| E5 | Гость закрыл браузер посреди голосования | Черновик восстанавливается из localStorage по возврату; до подтверждения голосом это не считается |
| E6 | Фото участника огромное (10 МБ) | Приём ≤5 МБ, авто-ресайз Pillow до 640 px / quality 80 (~100 КБ), хранение в БД (нет постоянного диска на free PaaS) |
| E7 | Часовые пояса | Храним UTC, отображаем в `TIME_ZONE` из env (таймзона площадки) |
| E8 | Админ завершил голосование по ошибке | Переход ЗАВЕРШЕНО→АКТИВНО запрещён (осознанно: результаты могли объявить). Только «Сброс голосов» + повторное прохождение состояния, либо полный сброс |
| E9 | Один участник в двух группах | Запрещено на уровне формы группы (валидация), чтобы не плодить споры «где его голос» |
| E10 | Результаты увидели до объявления | Результаты только в админке; публичная страница появляется только если админ нажал «Опубликовать» после ЗАВЕРШЕНО |

## 9. Приоритизация (MoSCoW)

**Must (без этого мероприятие не провести):**
- Голосование: 4 номинации + гран-при, правила уникальности, без регистрации, один голос на устройство (мягко)
- Статус-машина голосования + управление с двойным подтверждением
- Админка: логин, CRUD участников и групп, результаты таблицами + столбчатые диаграммы, полноэкранная страница диаграммы
- Экспорт CSV, опасная зона (сброс голосов / полный сброс)
- Мобильный хеллоуин-дизайн, тёмная тема, экраны всех состояний

**Should (делаем, если Must готов вовремя):**
- Фото участников/групп с ресайзом; черновик голосования; /healthz + пингер keep-warm
- JSON-экспорт; страница печати QR-кодов; публикация результатов гостям после завершения
- Журнал действий админа; детекция аномалий (счётчик дублей IP)

**Could (только если останется время):**
- Звуковые/конфетти-эффекты победы «уровня бог»; live-счётчик проголосовавших на дашборде с автообновлением; переключатель столбцы/линии на диаграмме; тёмно-светлая тема админки

**Won't (осознанно не в этой версии):**
- Регистрация/аккаунты/почта/SMS, мультиязычность, websockets-реалтайм, жёсткий антифрод (отпечатки устройств), кастомный домен (риск DNS за 2 дня), оплата/призы

| R7 | Падение Neon/Render | Низкая/Критич. | Контрольные точки CSV; план C — ноутбук + Cloudflare Tunnel за 10 минут |

## 11. Нефункциональные требования (обоснование — детали в ТЗ §8)

- **Производительность:** первый экран ≤2 с на 3G; целевой вес страницы <300 КБ; действие <300 мс. Запас нагрузки: 500 одновременных подключений (5× от ожидаемого).
- **Доступность:** ≥99,5 % в окно мероприятия; RTO ≤15 мин (план B/C готовы), RPO ≤5 мин (экспорт/PITR).
- **Безопасность:** HTTPS везде, CSRF, троттлинг логина и API, секреты только в env, персональные данные не собираются (псевдонимный токен; фото — с согласия участников, ответственность организатора).
- **Совместимость:** мобильный веб — iOS Safari 14+, Chrome Android 8+; десктоп — последние 2 версии Chrome/Firefox/Safari/Edge; вёрстка 320 px → 4K; тёмная тема по умолчанию (тёмный зал!).
- **Доступность (a11y):** контраст текста ≥4.5:1 (WCAG AA), тап-зоны ≥44 px, уважение к `prefers-reduced-motion`, семантическая разметка.
- **Поддерживаемость:** монолит на Django, один репозиторий, README с запуском, юнит-тесты на ядро правил голосования.

## 12. Глоссарий

| Термин | Значение |
|---|---|
| Номинация | Одна из 4 категорий конкурса (страшный/смешной/оригинальный/групповой) |
| Гран-при | Награда «Лучший костюм всего вечера», голосуется отдельно от номинаций |
| Участник | Соло-кандидат конкурса (карточка: номер, имя, описание, фото) |
| Группа | Групповой костюм (название + состав из участников) |
| Голосующий (voter) | Анонимный гость, идентифицируется токеном |
| Черновик | Несохранённые выборы гостя (localStorage до финального подтверждения) |
| Состояние голосования | НЕ НАЧАТО / АКТИВНО / ПАУЗА / ЗАВЕРШЕНО |
| Двойное подтверждение | Модалка с описанием последствий + ввод контрольной фразы |
| Аномалия | Признак накрутки: дубли IP-хэша, всплески, `голосов > гостей` |
