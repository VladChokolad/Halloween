# Памятка деплоя «Тыквоголос»

> Пошаговая инструкция для организатора/админа. Подробный фон — в
> `04-Инфраструктура-и-деплой.md` (далее — «04»). Здесь — только то, что нужно руками сделать.

---

## 1. Что деплоится (обзор архитектуры)

| Компонент | Что это | Где живёт |
|---|---|---|
| Django 5.2 | приложение «Тыквоголос» (гостевой голосовалка + админка) | Render, сервис **web**, runtime `python`, план **free**, регион **frankfurt** |
| Gunicorn | WSGI-сервер (`--workers 2 --threads 4 --timeout 90`) | стартует Render по `startCommand` из `render.yaml` |
| WhiteNoise | раздача статики (`CompressedManifestStaticFilesStorage`) — collectstatic при билде, gzip/brotli на лету | внутри того же процесса, без CDN |
| PostgreSQL 16 | единственная БД | **Neon**, free-тариф, **pooled connection string** (`...-pooler...neon.tech`, `sslmode=require`) |
| Билд-скрипт | `scripts/build.sh`: pip install → collectstatic → migrate | выполняется Render при каждом деплое |
| Health-check | `GET /healthz` → `ok` | Render пингует для подтверждения живости |

Ключевые файлы репозитория: `render.yaml` (Blueprint, §6.3 из 04), `scripts/build.sh`,
`requirements.txt`, `tykvogolos/settings/prod.py`, `.env.example` (шпаргалка по переменным).

---

## 2. Шаг 1 — создать БД на Neon

1. Регистрация на [neon.tech](https://neon.tech) → **Create project** (регион — ближайший к Frankfurt, например EU Central / aws eu-central-1).
2. Postgres 16 выбирается по умолчанию.
3. На дашборде возьмите **Pooled connection** строку (с `-pooler` в имени хоста) — она выглядит так:

   ```
   postgresql://USER:PASSWORD@ep-xxxx-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require
   ```

4. Обязательно сохраните её целиком: параметры `?sslmode=require` (и pooled-хост) должны остаться.
   НЕ берите direct-строку без `-pooler` — prod-настройки запрещают долгоживущие соединения (`conn_max_age=0`).

---

## 3. Шаг 2 — подключить репозиторий к Render (Blueprint)

1. Запушьте репозиторий на GitHub (GitLab тоже подходит).
2. Render → **New → Blueprint** → выберите репозиторий.
3. Render прочитает `render.yaml` и предложит создать сервис `tykvogolos` (python, free, frankfurt,
   build `./scripts/build.sh`, start gunicorn, health-check `/healthz`).
4. Все переменные с `sync: false` Render попросит ввести вручную — это секреты, см. таблицу ниже.
5. Нажмите **Apply** — начнётся первый деплой.

---

## 4. Шаг 3 — секреты в Render → Environment

Заполняется на шаге Blueprint либо потом: сервис → **Environment** → Add/Edit → **Save changes**.

| Переменная | Значение | Обязательность |
|---|---|---|
| `SECRET_KEY` | `openssl rand -hex 32` (любой длинный случайный). **Никогда не коммитить** | **обязательная** — без неё prod-настройки падают с внятной ошибкой |
| `DATABASE_URL` | pooled-строка Neon из шага 1 (`...-pooler...&sslmode=require`) | **обязательная** — без неё ошибка, тихого sqlite-дефолта в prod больше нет |
| `ALLOWED_HOSTS` | `tykvogolos.onrender.com` (домен Render; позже через запятую добавить свой домен) | **обязательная** |
| `CSRF_TRUSTED_ORIGINS` | `https://tykvogolos.onrender.com` (схема `https://` обязательна) | нужна для POST-форм админки; для API — не критична |
| `ADMIN_LOGIN` | `max` | **обязательная** (из неё seed создаёт superuser) |
| `ADMIN_PASSWORD` | `max` (демо; для реального события — `openssl rand -base64 18`, передать организатору лично) | **обязательная** |
| `ADMIN_EMAIL` | `max@example.com` → заменить на реальный | опциональная (дефолт в коде) |
| `TIME_ZONE` | `Europe/Moscow` | опциональная (дефолт в коде) |
| `DEBUG` | `0` | уже задан в `render.yaml` |
| `VOTER_COOKIE_DAYS` | `30` | уже задан в `render.yaml` |
| `SOFT_IP_LIMIT` | `0` (площадка за общим NAT — лимит выключен; см. 04 §Т2) | уже задан |
| `VOTE_RATE_LIMIT` | `10` (POST /api/v1/vote в минуту с одного IP) | уже задан |
| `PHOTO_MAX_MB` | `5` | уже задан |
| `LOGIN_MAX_ATTEMPTS` | `5` | уже задан |
| `LOGIN_LOCK_MINUTES` | `10` | уже задан |

Пометка: значения «уже задан» прописаны в `render.yaml` и в Blueprint вводить не нужно, но при
редактировании Environment их можно менять без правки кода.

## 5. Шаг 4 — первый деплой

1. Render выполняет `./scripts/build.sh`:
   - `pip install -r requirements.txt`;
   - `python manage.py collectstatic --noinput` — статика сжимается в `staticfiles/`;
   - `python manage.py migrate --noinput` — схема БД на Neon.
2. Затем стартует gunicorn; Render считает сервис живым, когда `GET /healthz` вернёт `ok`.
3. Смотреть прогресс: сервис → **Events/Logs**. Холодный первый билд — 3–5 минут.

---

## 6. Шаг 5 — создать админа и наполнить каталог

### 6.1. Демо-вариант (сухой прогон)

Render → сервис → вкладка **Shell** → выполнить:

```bash
python manage.py seed_demo
```

Команда (idempotent, можно запускать повторно):
- создаёт superuser `max` с паролем из `ADMIN_PASSWORD` (по умолчанию `max`) для `/django-admin/`;
- заполняет каталог: 8 демо-участников и 2 группы («Вдова Мортис», «Семейка Аддамс» и т.д.).

### 6.2. Реальный каталог (продакшен)

**Важно:** `fixtures/catalog.example.json` — это «золотая копия» в **кастомном формате**
(ключи `participants`/`groups`, нет полей `model`/`pk`), Django `loaddata` его **не съест**.
Два пути:

- **Путь А (рекомендуемый): ручной ввод через `/admin/`.**
  Войдите в `/admin/` → «Участники» → добавить каждого (номер, имя, описание), затем «Группы».
  Файл `fixtures/catalog.example.json` удобно использовать как шаблон: скопировать имена/номера.
  Фото загружаются прямо в карточке участника (≤ `PHOTO_MAX_MB`, ресайз до 640 px автоматом).
- **Путь B: если когда-нибудь появится совместимая фикстура** (полноценная Django-fixture с
  `"model": "core.participant"`), тогда:

  ```bash
  # Render → Shell
  python manage.py loaddata fixtures/<файл>.json
  ```

  Текущий `catalog.example.json` в таком формате не лежит, поэтому `loaddata` на него
  выполнять не нужно — упадёт с ошибкой десериализации (данные при этом не портятся).

## 7. Шаг 6 — финальная проверка

- [ ] `https://<домен>/healthz` → тело `ok`
- [ ] `https://<домен>/` → гостевой экран корректного состояния (`NOT_STARTED` и т.д.)
- [ ] `https://<домен>/admin/` → логин `max` / пароль из `ADMIN_PASSWORD` работает
- [ ] `/django-admin/` (бэкдор) → тот же `max` входит как superuser
- [ ] Сухой прогон: `/admin/state/` старт с контрольной фразой → голос с телефона → результат виден

## 8. Свой домен (опционально)

1. Render → сервис → **Settings → Custom Domains** → Add → впишите домен, добавьте CNAME-запись у регистратора (Render покажет значение, обычно `tykvogolos.onrender.com`).
2. Дождитесь выпуска TLS-сертификата (автоматически, Let's Encrypt).
3. **Обязательно** обновите переменные (Environment → Save — автодеплой не нужен, env применяется рестартом):
   - `ALLOWED_HOSTS` = `tykvogolos.onrender.com,ваш-домен.ru` (через запятую, без схемы);
   - `CSRF_TRUSTED_ORIGINS` = `https://tykvogolos.onrender.com,https://ваш-домен.ru` (со схемой `https://`).
4. Без пункта 3 гостевые страницы будут отдавать 400 (DisallowedHost), а админка — CSRF-ошибку.

## 9. Пингер для дня события (cron-job.org / UptimeRobot)

Render free засыпает после ~15 минут без запросов (холодный старт 30–60 с), Neon засыпает через
5 минут простоя. Пингер держит обе системы тёплыми.

1. [cron-job.org](https://cron-job.org) → Create cronjob → URL `https://<домен>/healthz`, GET, интервал 1–5 мин.
2. (Контроль) [UptimeRobot](https://uptimerobot.com) → New monitor → HTTP(s) → тот же URL, 5 мин. Бонус — публичная status-страница.
3. **⚠️ Экономия CU-часов Neon (04 §7.3):** круглосуточный пингер выжигает месячный лимит Neon free
   (~100 CU-ч) за несколько дней. Расписание:
   - создаются оба пингера заранее — **на паузе**;
   - включаются **T-1, ~17:00** (после финального деплоя);
   - выключаются **через ~2 часа после конца события** (пункт в чек-листе демонтажа, 04 §12).

## 10. Регламент дня мероприятия

| Момент | Действие |
|---|---|
| До старта | Пингеры включены; `/healthz` зелёный; каталог выверен; сделан экспорт-бэкап (см. ниже) |
| Старт | `/admin/` → «Начать голосование», ввести контрольную фразу (сервер перепроверяет её повторно) |
| Пауза | `/admin/` → «Пауза» (гости видят экран паузы, голоса не принимаются) |
| Финиш | `/admin/` → «Завершить» → `/results` открывается после включения «публиковать результаты» |
| **Перед любым опасным действием** | сброс голосов / полный сброс — только после **экспорта**: `/admin/export/` → CSV+JSON (голоса, участники, группы). Без бэкапа кнопки «Опасной зоны» не трогать |
| Бэкап БД | (а) регулярный экспорт CSV/JSON из админки; (б) полный бэкап: Neon Console → Point-in-time restore / `pg_dump "$DATABASE_URL" -Fc -f backup.dump` с локальной машины |
| После события | выключить пингеры; финальный экспорт; (опционально) Manual Suspend сервиса в Render, чтобы не тратить 750 instance-часов |

## 11. Обновление версии и откат

- **Обновление:** `git push` → Render автоматически пересобирает (autoDeploy) → `build.sh` (pip → collectstatic → migrate) → новая версия live. Миграции применяются при билде, т.е. даунтайм минимален.
- **Откат:** Render → сервис → **Events** → найти предыдущий удачный деплой → **Rollback**. Откат возвращает предыдущий образ кода; миграции БД автоматом не откатываются — помните об этом при schema-changing релизах.
- На этапе T-1 (финальный деплой) автодеплой можно выключить (04 §6.3: `autoDeploy: true` → выключить после T-1), чтобы случайный push не перезаписал прод в день события.

## 12. Troubleshooting (типовые ошибки)

| Симптом | Причина | Что делать |
|---|---|---|
| `/` грузится 30–60 с, потом открывается | Холодный старт Render free / сон Neon | Норма после простоя. Проверить, что пингер включён (§9) |
| `400 Bad Request (DisallowedHost)` после смены домена | Домен не в `ALLOWED_HOSTS` | Environment → добавить домен (без схемы) → Save |
| CSRF-ошибка в админке после смены домена | Домен не в `CSRF_TRUSTED_ORIGINS` | Environment → добавить `https://домен` (со схемой!) → Save |
| `502 Bad Gateway` | Gunicorn упал/перезапустился | Render → Logs: смотреть трейсбек. Один раз — поднимется сам; циклично — **Rollback** на предыдущий деплой |
| `500` c «Missing staticfiles manifest entry» | Новый файл статики добавлен после collectstatic, либо `staticfiles/` не собрался | Перезапустить деплой (Manual Deploy → Deploy latest commit); убедиться, что build.sh дошёл до collectstatic |
| `/healthz` отвечает 503 / Neon «compute suspended» | CU-часы Neon исчерпаны (пингер забыт включённым) | Neon Console → возобновить/ждать обновления лимита; данные не теряются; впредь соблюдать расписание §9 |
| `429 Too Many Requests` при голосовании | Сработал `VOTE_RATE_LIMIT` (10 POST/мин с IP) — например, все гости за одним NAT-адресом Wi-Fi площадки | Проверить, что лимит адекватен числу гостей за одним NAT; при необходимости поднять переменную и Save (применится после рестарта). Мягкий IP-лимит (`SOFT_IP_LIMIT`) по умолчанию выключен именно по этой причине |
| Первый запрос к БД «висит» ~5 с | Neon compute проснулся | Норма при простое > 5 мин; лечится пингером |
| Деплой падает на migrate | Кривая миграция / БД недоступна | Render → Logs; проверить `DATABASE_URL` (pooled, `sslmode=require`) |

Диагностика всегда начинается с двух мест: **Render → Logs** и **UptimeRobot** (статус-страница).
